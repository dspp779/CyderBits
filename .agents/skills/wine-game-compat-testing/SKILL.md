# Wine 遊戲相容性測試

將「看到什麼」、「實際載入什麼」與「哪項改動改變結果」連結起來。先處理使用者指定且可重現的畫面；已縮小範圍後，不繼續漫遊其他模式或教學。

## 開始測試

- 讀工作區 AGENTS.md，確認 app 與 engine 的責任邊界。Cyder app 啟動層可修環境與診斷；Wine 原始碼／建置移到 engine repo，遵守該處指示。
- 確認實際工具：先用可用的 computer-use；若它無法辨識 Wine，再用 [macOS 操作方式](references/macos-controls.md)。不要因使用者標記插件，就聲稱工具已可用。
- 記錄遊戲／啟動器、引擎、實際圖形後端、OS／晶片、prefix、資料下載狀態及重現畫面。公開報告不包含本機使用者路徑、帳號或憑證。
- 保留當前設定、已開視窗與程序識別。優先使用獨立 bottle；若使用既有 bottle，明確記錄測試會保存的進度或設定。使用者允許遊玩不等於允許消費、抽卡、刪檔或公開發文。

## 操作與驗證

Wine 的 Dock 名稱可只有 `wine`，bundle ID 可為空，AX 可沒有遊戲按鈕。用標題、PID、window ID、引擎 executable 與新截圖交叉確認；啟動器 PID 通常不同於遊戲 PID。

`scripts/wine-windows.swift` 列出權限和可見 Wine 視窗；`scripts/guarded-click.swift` 提供經驗證的單次原生點擊。先預覽，只有明確加 `--click` 才啟用輸入。腳本拒絕不符的 PID／window ID／標題、負數或超界座標；輸入前需是最前方目標視窗。點擊回傳成功只代表事件已送出，仍須新截圖確認 UI 結果。

若權限缺失，說明需要 Screen Recording 或 Accessibility／裝置控制，以及授權對象；請使用者在系統設定開啟。不要修改 TCC 資料庫。若目標驗證失敗，重新觀測，不盲目重試或改點其他 Wine 視窗。不要用共享 wineserver 的全域終止方式關遊戲。

## 受控診斷

讀 [對照與紀錄](references/diagnostic-matrix.md)，依問題選最小實驗：

- 一次改一類變因，保持相同場景、遊戲檔案、下載狀態與其他設定。
- 後端名稱不等於實際載入；用遊戲程序的模組與紀錄確認。
- UI 正常、影片白底，不足以推定主要 3D 渲染失敗。先區分媒體元件探索、解碼、輸出格式與材質呈現。
- factory 存在不等於成功解碼；送出輸入不等於完成操作；不同場景或 FPS 上限不能用來排名效能。
- 使用程序限定、可還原的環境；不把單一遊戲的假說變成全域 DXMT 設定或遊戲二進位修改。

遇到 GStreamer 搬移路徑或 H.264 問題時，再讀 [賽馬娘案例](references/umamusume-case.md)。案例是已驗證環境中的證據，不是所有遊戲的通用修正。
