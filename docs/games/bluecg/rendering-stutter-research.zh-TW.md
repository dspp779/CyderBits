# 水藍魔力更新後卡頓：繪圖路徑與實測計畫

> 整理日期：2026-10-30。本文是回報與候選原因的整理，尚未在原回報機器完成受控重測。

追蹤：[CyderBits #15：驗證 BlueCG `no3d` 的效能改善](https://github.com/dspp779/CyderBits/issues/15)。

## 回報與目前可確認的範圍

使用者表示，某次更新後水藍魔力明顯卡頓；將 `bluecg.exe` 的 WineD3D renderer 改為 `no3d` 後，三開遊戲時觀察到的 CPU 使用率約從 160% 降至 50%，差值為 110 個百分點、相對降幅約 69%。目前缺少更新前後的客戶端版號、Cyder／引擎版本、相同場景的逐程序 CPU 與 frame-time 紀錄，因此這組數字是有效線索，不宜當成普遍效能保證。

BlueCG 使用 DirectDraw。Cyder 的現有 `bluecg` recipe 設定 `renderer: builtin`、Retina 與 192 DPI，未指定 WineD3D 的 `no3d`；現有 CompatDB 也沒有 BlueCG 的 renderer 規則。WineD3D 的 `gl` 是預設 renderer，`gdi`／`no3d` 是 GDI 繪圖路徑。Cyder 沿用 Wine 的預設選擇。[Wine 6.0 發行說明](https://www.winehq.org/announce/6.0)

`no3d` 改變的是 WineD3D renderer；啟動腳本的 `--soft3d` 改變的是遊戲參數 `3Ddevice:0`。兩者必須分別測量。較低的 CPU 數字也不能單獨證明每次卡頓都由 GPU 讀回造成；需要相同場景的幀時間與 trace 才能定位。

## 哪些更新值得先查

| 時間 | 已公布的變動 | 與回報的關係 |
|---|---|---|
| 2026-09-21 | 客戶端加入透明圖像、動畫資源及較大型圖檔支援，並調整字型顯示處理。 | **首要候選起點**：與使用者提到的半透明、新動畫吻合；尚未證實增加了 Wine 的畫面讀回次數。 |
| 2026-09-27 | 修正文字／陰影重複繪製與字型資源管理，公告稱改善長時間執行的卡頓。 | 若卡頓隨遊玩時間惡化，應優先區分資源累積與 renderer 成本。 |
| 2026-09-28～30 | 改善視窗縮放；新增隱藏其他玩家與寵物的選項。 | 視窗尺寸、可見角色數與畫面像素量都是對照變因。 |
| 2026-10-05～11 | 補強動畫、圖片裁切與清理；10/11 減少透明圖檔及多人場景的重複處理。 | 可能改變同一場景的工作量；測試須記錄確切客戶端版本。 |
| 2026-10-18～22 | 調整登入／切圖畫面等待、介面重複繪製和地圖更新卡頓。 | 若主要症狀在切圖、聊天或大地圖，應與持續掉幀分開測。 |

以上日期與內容依 [BlueCG 官方更新公告](https://www.bluecg.net/forum.php?mod=viewthread&tid=822152)。公告只證明版本改動，無法單獨判定哪次更新引入此回報的卡頓。若回報者的最後正常日期早於 9/21，先比較 9/21 前後；若較晚，再依實際更新日縮小範圍。官方下載頁目前提供 2026-10-29 更新檔，但啟動器、核心與圖檔各自更新，啟動器版號未變不代表內容未變。[BlueCG 下載與修復說明](https://www.bluecg.net/download/gamedl.html)

Cyder 端另有一個要排除的變因：0.9.5 把 RetinaMode 與 192 DPI 改為新 bottle 的預設；它發生於 9/21 遊戲改動之前。若回報者同時更新 Cyder 或重建 bottle，應把 Retina／DPI 與遊戲更新分開比較。0.14.0-rc.1 的公告則記載沿用 0.13.2 的引擎與圖形封存檔，沒有宣稱遊戲幀率改善。見本 repo 的 `docs/releases/v0.9.5.md` 與 `docs/releases/v0.14.0-rc.1.md`。

## 後續實測路徑

1. **固定版本與場景。** 在原回報環境記錄 macOS／晶片、Cyder 與 Wine engine 版本、遊戲主程式與啟動器版本、更新日期、啟動模式、經典／HD、Retina／DPI、視窗大小、三開與單開的場景。遊戲檔以雜湊或檔案版本識別。先用目前可重現版本測；若合法持有舊版快照，再比較更新前後，不覆蓋現有遊戲目錄。
2. **先做 renderer 的 A/B/A。** 使用獨立 bottle 或可還原的設定副本；在相同地圖、角色密度、視角與視窗大小下依序測 `gl`、`gdi`（同 `no3d`）、還原 `gl`。每組重新啟動遊戲；先單開，再三開。若 A/B/A 能重現相同方向的差異，才可較有把握歸因於 renderer 選擇。
3. **量測體感與成本。** 每組先暖機，再錄固定時長；記錄每個 `bluecg.exe`、`wineserver` 與相關程序的 CPU、總 CPU、幀時間分布（至少中位數及 95/99 百分位）、長幀次數、記憶體與 GPU 活動。登入、切圖、多人場景、戰鬥特效、長時間掛機各留一個固定重現流程；不把不同場景的 CPU 數字直接比較。記錄畫面清晰度、縮放、Alt+Enter、最小化／還原是否退化。
4. **確認實際路徑。** 核對 `bluecg.exe` 的 PID、載入的 `ddraw.dll`、WineD3D renderer 與 log；啟動器 PID 不能代替遊戲 PID。只在必要時收窄 `+ddraw,+wined3d` 診斷，避免大量 log 本身改變效能。既有 BlueCG GL／GDI 路徑與 GDI 縮放畫質限制見 `docs/bluecg-winemac-resize-black-screen.md`。
5. **再拆遊戲設定。** 在已選定的 renderer 下，一次只切一項：經典／HD、啟動模式、隱藏其他玩家與寵物、Retina／DPI、視窗尺寸。由官方建議的經典 `[5]` 或 HD `[5]` 起測；模式 `[1]`、`[2]` 作對照，`[3]`、`[4]` 屬相容性測試模式。官方模式說明見 [啟動器使用與更新說明](https://www.bluecg.net/new/BlueCG_Launcher.html)。

驗收時至少要同時滿足：同場景 A/B/A 的幀時間與長幀改善可重現、三開 CPU 改善、登入與切圖正常、畫面未破圖、視窗操作可接受。只看到 CPU 降低但幀時間未改善，不足以宣稱卡頓已解決。

## 可採用的遊戲專屬設定

| 設定 | 現況與建議 |
|---|---|
| WineD3D `gdi`／`no3d` | 回報者已見效，適合作 BlueCG **候選**設定。先在原環境做 A/B/A，並檢查縮放模糊等畫質折衷；不要設成所有遊戲的預設。 |
| Cyder CompatDB | 引擎已支援 `actions.wined3d_renderer: gdi`，可用 `\\bluecg.exe` 尾綴限定遊戲主程式，不影響 `BlueLauncher.exe`。驗收後再啟用規則及測試，並確認實際發佈的 engine 含此能力。 |
| 啟動模式 | 依官方建議先用經典 `[5]`／HD `[5]`；保持相同模式比較 renderer。`[2]` 的 D3D 軟體運算與 Wine `no3d` 是不同設定。 |
| `Hide Other Players and Pets` | 多人場景可另測開／關；它會改變畫面內容，不能在 renderer A/B 期間同步切換。 |
| Retina／DPI、視窗尺寸 | 可作第二階段對照。既有紀錄指出 GDI 縮放可能模糊；若採 GDI，先在進遊戲前調好尺寸，驗收實際畫質。 |
| 原生 `DDRAW.dll` 與 `--soft3d` | 先保持目前來源與遊戲參數不變；若 renderer 對照無法解釋問題，再單獨測。 |

**決策點：**在受控重測前，保留 Wine 預設與現有 BlueCG recipe；可以提供回報者暫用的 `gdi`／`no3d` 選項。若多台原回報環境均通過上述驗收，再考慮啟用 `bluecg.exe` 專屬 CompatDB 規則，並附上還原方式。此規則是應用層設定，不需先修改 Wine 引擎原始碼。
